# 酒店服务平台架构与V1改造说明

平台围绕酒店提供各类服务。服务机构入驻平台，各自维护自己的酒店，按开通的应用为酒店提供服务。第一版上线共享保洁，之后陆续接入接送、洗涤、维修、配餐等。

## 一、整体架构

```
平台（我们管理）
    机构管理  │  应用管理  │  区域（景区）  │  字典与系统参数  │  公众号 / 小程序 / 控制台模板  │  全平台统计

机构（入驻的服务商，数据互相隔离）
    开通的应用  │  酒店、房间、酒店人员  │  本机构人员与角色  │  公众号 / 小程序  │  控制台  │  价格、订单、账目

应用（机构按需开通）
    共享保洁【V1】  │  酒店接送（后续）  │  洗涤（后续）  │  维修（后续）  │  配餐（后续）

使用入口（以手机为主）
    机构的公众号 / 小程序  │  电脑管理后台

```

## 二、关键设计

| 项 | 说明 |
| --- | --- |
| 机构 | 一家服务商就是一个机构。机构之间数据完全隔离，平台管理员可以查看全部。 |
| 应用 | 一个应用是一套完整的服务功能。机构可以开通多个应用，开通后对应的菜单、手机端入口、控制台组件自动出现。 |
| 酒店 | 由机构自己维护，属于机构的私有数据，其他机构看不到。同一机构开通多个应用时，共用同一批酒店。酒店人员的账号也在该机构下。 |
| 区域（景区） | 区域由平台统一维护，景区是区域的一种类型，目前只有四姑娘山。区域是酒店上的一个属性：共享保洁要求必填，机构可按区域管理名下酒店和保洁员，一个机构可以服务多个区域；其他应用可以不填。以后在其他地方开展业务时，增加新的区域或区域类型即可。 |
| 公众号 / 小程序 | 每个机构可以对接并配置自己的公众号或小程序：账号参数、菜单、消息模板。菜单按机构开通的应用自动生成，机构可以再调整。酒店人员、保洁员从本机构的公众号或小程序进入。 |
| 控制台 | 每个机构有自己的控制台首页，由统计卡片、待办、快捷入口等组件拼成。平台按应用提供默认模板，机构可以自己增减和排列组件。电脑端和手机端各一套。 |
| 账号 | 同一个手机号可以在多个机构下工作，登录时选择机构。 |

## 三、后续服务怎么接入

各项服务的流程骨架相同：酒店下单 → 机构派给人 → 执行 → 酒店验收评价 → 月度对账。派单、评价、对账、消息提醒做成通用能力，新服务主要是定义自己的单据内容。

每新增一项服务就是新增一个应用，包含：

- 后台菜单和权限
- 手机端页面和入口
- 公众号菜单模板和消息模板
- 控制台组件
- 默认角色

机构勾选开通后即可使用，底座不用改。

## 四、V1 改造说明

| 模块 | 怎么改 | 说明 |
| --- | --- | --- |
| 技术底座 | 现有 Node 后端换成 Java 开源框架（ruoyi-vue-pro），数据库继续用 MySQL。 | 注入漏洞、密钥随代码存放、无测试等问题从底层解决；可随业务量扩展。 |
| 机构 | 后台手工开通改为机构自助注册、平台审核后自动开通。 | 数据隔离由框架自动完成，不再靠每个接口手写。 |
| 应用管理 | 保留。应用从「一组后台菜单」扩成完整功能包，包含手机端入口、公众号菜单模板、控制台组件、默认角色。 | 以后上维修、配餐等只需新增应用。 |
| 酒店 | 保留机构各自维护的方式。新增「所属区域（景区）」属性。 | 与现有做法一致，旧数据可直接迁移。 |
| 公众号 / 小程序 | 保留按机构配置。菜单和消息模板改为按开通的应用自动生成。 | 机构开通新应用后不用再手工配菜单。 |
| 控制台 | 保留「组件 + 组装」的做法。改为机构可自行调整，并增加手机端控制台。 | 现在只有电脑版，且由平台管理员统一拼装。 |
| 共享保洁 | 按现有流程重写：酒店录单、派单、完工、对账。 | 新增到场打卡、酒店验收、评价；派单时保洁员按评分排序；按酒店和房型定价并写入订单。 |
| 平台统计 | 新增。按区域（景区）、机构、月份汇总单量和金额，可导出。 | 作为第三方返点的依据；不做线上支付。 |
| 旧系统 | 迁移期间继续运行，其他业务线暂不动。 | 一条业务线在新平台验收后再切换。 |

### 阶段与粗估工期

| 阶段 | 工期 |
| --- | --- |
| 底座搭建 | 1 周 |
| 机构、应用、基础数据移植 | 3 周 |
| 手机端、公众号 / 小程序、控制台 | 3 周 |
| 保洁主数据：酒店、房间、保洁员、定价 | 2 周 |
| 保洁订单与评价 | 4 周 |
| 对账与统计 | 2 周 |
| 试点上线 | 2 周 |
| 合计 | 约 17 周 |

### 第一版不做

- 接送、洗涤、维修、配餐等其他应用
- 线上支付
- 保洁员抢单、自动派单

## 五、需要确认

1. **机构自有小程序的发布方式**：公众号可以直接按机构配置。小程序每个账号都要单独提交微信审核，同一套代码需要为每个机构各发布一次。建议第一版先支持机构自有公众号，并提供一个平台小程序供没有自己小程序的机构使用；机构自有小程序按需逐个发布，数量多了再接入微信第三方平台做批量发布。
2. **同一家酒店被两个机构录入**：酒店由机构各自维护后，系统不会阻止两家机构录入同一家酒店。「一家酒店只对接一家众包商」建议作为业务约定，不由系统强制。
3. **工期与投入**：约 17 周，按 2 名后端 + 1 名前端/小程序开发粗估。
