# 酒店服务平台：现有架构、V1 方案与后续考虑（开发版）

平台围绕酒店提供服务。服务机构入驻后各自维护自己的酒店，按开通的应用提供服务。V1 只上线共享保洁，之后陆续接入接送、洗涤、维修、配餐。

本文分三部分：现有 Node 系统是怎么做的、V1 准备怎么做、后续要提前考虑的事。

> 现有系统部分来自源码通读和线上后台只读调研。V1 中关于开源框架的判断基于对 ruoyi-vue-pro 的了解，**尚未对照选定版本的源码逐项验证**，开工第一步需要做这件事。

## 1. 现有系统

### 1.1 技术栈与规模

| 项 | 现状 |
| --- | --- |
| 后端 | Node.js + Express，`mysql` 驱动直连，`socket.io` 推送，`node-schedule` 定时任务，单进程 |
| 前端 | Vue 3 + Vuex + Element Plus（后台）；公众号内 H5（`/mobile`）给酒店、保洁员、司机用 |
| 外部依赖 | 七牛云存储、阿里云短信、微信公众号 / 小程序 / 支付、C-Lodop 打印 |
| 规模 | 约 1.7 万行，99 张表，约 325 个接口，329 个权限点 |

### 1.2 代码结构

```
router/
  platform/        登录、机构、应用、菜单、角色、用户、字典、参数、公众号、控制台、通知、定时任务
  base_data/       酒店、保洁员、司机、车队、车辆、客户、商品、商家 …
  order_center/    保洁单、接送单、布草单、电商订单、评价 …
  bill/            账单、绩效
  work_panel/      控制台各统计组件的数据接口
  wechat/          微信回调
common/
  sql_unit.js      拼 SQL 的工具（insert / update / 搜索条件）
  common.js        鉴权、权限校验、字典翻译、统一响应
  data_cache.js    进程内缓存（酒店、机构、公众号配置等）
  socket_methods.js / timed_task_methods.js
wechat_tool/       公众号、小程序的 access_token、模板消息、菜单
token/ pem/ qiniu/ ali_msg/
```

### 1.3 核心机制

**认证**

- 前端先取 RSA 公钥，密码加密后登录。
- token 是自制格式：`base64(payload).HMAC`，payload 里带 `id`、`organ_id`、`client`、`appid`，有效期 30 天。
- 每个客户端类型只保留一个有效 `token_id`，在别处登录会把之前的挤掉。
- 登录方式：账号密码、短信验证码、小程序 `code`、公众号 openid。微信身份存在 `wx_user`，与用户的绑定存在 `wx_platform(wx_id, user_id, app_id)`。

**多机构**

- 机构 `core_organ`，用户与机构的关系 `core_user_organ`。登录时取查到的第一条，实际效果是一个用户只属于一个机构。
- 数据隔离靠每条 SQL 手写 `organ_id = ?`，`organ_id` 从 token 里取。没有统一拦截。
- 机构 id 为 `-1` 的是平台自身，全局默认配置挂在它名下。

**应用与权限**

| 表 | 含义 |
| --- | --- |
| `core_application` | 应用 |
| `core_app_resource` | 应用包含哪些菜单和操作 |
| `core_organ_app` | 机构开通了哪些应用 |
| `base_menu` | 两级菜单，带前端路由和组件路径 |
| `base_operation` | 菜单下的操作，带 `req_url`，权限码为 `模块.菜单.操作` |
| `core_role` / `core_user_role` / `core_permission` | 角色、用户角色、授权记录（可对角色授权，也可直接对用户授权） |

**字典与参数**

- `base_dict` / `base_dict_item`：字典项带 `organ_id`，`-1` 为全局，机构可覆盖。接口返回里的 `xxx_value` 是字典翻译结果。
- `system_config` / `system_config_value`：参数定义与取值分开，取值按机构存，取不到用 `-1` 的全局值。

**控制台（工作台）**

- `base_template`：统计组件，共 23 个，每个对应一个前端组件和一个 `work_panel/` 下的数据接口。
- `core_workPanel` + `core_workPanel_detail(template_id, width, height, sort)`：把组件拼成一套控制台。
- `workPanel_organ`：把控制台分配给机构，一个机构只能有一套。
- 取「我的控制台」时还会按权限过滤组件。
- 只有电脑端，由平台管理员统一拼装，机构自己不能调。

**公众号 / 小程序**

- `wx_config`：按机构登记，字段包括类型（公众号 / 小程序）、`app_id`、`app_secret`、手机端网址、`msg_tem`（模板消息 id 的 JSON）、`menu_obj`（公众号菜单 JSON）、微信支付商户参数。
- 公众号菜单在后台编辑后调用微信接口推送。
- 酒店入口是一个带 `stateJson` 的链接或二维码，里面加密了「机构 id, 酒店 id, appId」，用来识别来源。
- 新单、完工等通过公众号模板消息通知。

### 1.4 保洁业务

| 表 | 主要字段 |
| --- | --- |
| `base_hotel` | `organ_id`, `name`, `tel`, `status`, `public`, `half_able`, `limit_able`, `state_json` |
| `hotel_room` | `hotel_id`, `name`, `floor`, `price`, `rate`, `default_data` |
| `hotel_user` | `hotel_id`, `user_id`, `type`（负责人 / 普通） |
| `base_cleaner` | `organ_id`, `cleaner_id`（→ `core_user.id`）, `status` |
| `room_order` | `organ_id`, `hotel_id`, `date`, `num`, `amount`, `status`, `payment_status`, `annex`, `remark` |
| `room_order_detail` | `room_order_id`, `name`（房间）, `tag`（JSON，含下单时的价格）, `status`, `user_id`（JSON 数组，可多人）, `room_round`, `warning`, `annex`, `remark` |

流程：

1. 酒店人员从公众号进入，每天建一张 `room_order`，往里加房间明细。机构负责人也可代录。
2. 机构负责人收到模板消息，单间或整单派给保洁员，可撤回。保洁员也可以自己接待接单的房间。
3. 保洁员或负责人标记完成，酒店收到通知。明细全部完成或取消后，主单自动变为已完成。
4. 可标记查房结果、异常、取消。
5. 机构在后台标记收款，不走线上支付。

明细状态：`pendAccept → accepted → completed`，另有 `giveup`、`unusual`。主单状态：`in_progress → completed`。

### 1.5 已知问题

| 问题 | 位置 |
| --- | --- |
| SQL 由字符串拼接，查询参数名和值、更新字段都直接进 SQL | `sql_unit.js` 的 `searchSql`、`updateParam`，全系统通用 |
| 数据库口令、微信支付证书、登录私钥、token 密钥都在仓库里 | `db/`、`wechat/`、`pem/`、`token/` |
| 密码是无盐 SHA1，默认密码为手机号后六位 | `sql_unit.js` 的 `addUserFilter` |
| 接口把 `app_secret`、商户密钥原文返回给前端 | `platform/wx_app` |
| 部分接口没有鉴权；洗涤等多处把机构 id 写死为 `-1` | `base_data/customer_manage`、`order_center/linen_*` |
| 异常时把数据库报错原文返回 | 各路由的 `catch` |
| 缓存在进程内存里，无法多实例部署 | `data_cache.js` |
| 开启了多语句执行；无自动化测试；无数据库变更脚本 | `db/mysql.js` |

## 2. V1 方案

### 2.1 目标架构

```
平台（我们管理）
    机构管理 │ 应用管理 │ 区域（景区） │ 字典与参数 │ 公众号/小程序/控制台模板 │ 全平台统计

机构（= 租户，数据互相隔离）
    开通的应用 │ 酒店、房间、酒店人员 │ 人员与角色 │ 公众号/小程序 │ 控制台 │ 价格、订单、账目

应用（机构按需开通）
    共享保洁【V1】 │ 酒店接送 │ 洗涤 │ 维修 │ 配餐

入口
    机构的公众号 / 小程序（手机为主） │ 电脑管理后台
```

### 2.2 技术选型

| 项 | 选择 |
| --- | --- |
| 后端底座 | ruoyi-vue-pro 单体版（Spring Boot 3，JDK 17 或 21，MyBatis-Plus） |
| 数据 | MySQL + Redis；文件继续用七牛（走框架的 S3 兼容存储） |
| 管理后台 | 框架自带的 Vue 3 + Element Plus 版本 |
| 手机端 | uni-app（Vue 3），一套代码发小程序和公众号 H5 |
| 模块划分 | 框架的 system / infra / mp 保留；商城、CRM、ERP、工作流等先不引入；业务按应用分 Maven 模块 |

### 2.3 概念映射

| 现有 | V1 | 说明 |
| --- | --- | --- |
| 机构 `core_organ` | 租户 | 行级隔离，框架自动加 `tenant_id` 条件 |
| 应用、应用-菜单 | 自建「应用」表 | 框架的租户套餐是一租户一套餐，不满足多应用，见 2.4 |
| 机构-应用 | 自建「租户-应用」表 | 租户可用菜单 = 所开通应用的菜单并集 |
| 菜单 + 操作 | 框架菜单表（目录 / 菜单 / 按钮） | 旧菜单对应旧页面，不迁移，随新页面新建 |
| 角色、用户角色 | 框架自带 | 「直接对用户授权」不保留，统一走角色 |
| 用户 | 框架后台用户表 | 保洁员、酒店人员都用它，需要角色和租户归属 |
| 字典、参数 | 框架自带 | 按机构覆盖字典项的能力需自己加，V1 先不做 |
| 定时任务、文件、短信、日志 | 框架自带 | |
| 公众号配置 `wx_config` | 框架 mp 模块的公众号账号 + 自建小程序账号配置 | 按租户存，密钥加密、不回显 |
| 控制台 | 自建 | 框架没有对应功能 |
| 通知任务 + socket.io | 框架站内信 + WebSocket + 微信消息 | |

### 2.4 需要改动或补充框架的地方

1. **一个机构开通多个应用。** 新增应用表和租户-应用表，改掉租户服务里「按套餐取菜单」和「套餐变更后同步租户角色菜单」两处逻辑。
2. **机构自助注册与审核。** 新增申请表和审核流程，审核通过后调用框架已有的创建租户逻辑，并开通默认应用、建默认角色。
3. **后台用户的微信登录。** 框架的小程序 / 公众号登录主要在会员端，后台用户端需要补：小程序手机号登录、公众号 openid 绑定登录。
4. **一个手机号属于多个机构。** 确认框架里用户名、手机号的唯一性范围；登录后按手机号列出可进入的机构供选择。
5. **平台管理员跨租户。** 平台统计类查询要显式忽略租户条件，并限定只有平台管理员可调用。

### 2.6 V1 关键设计

**区域（景区）**

- `area` 带类型，景区是其中一种。目前只有四姑娘山一条。
- 区域是酒店上的属性。应用上有「是否要求区域」的配置：共享保洁为是，新建或编辑酒店时必填；其他应用可空。
- 机构服务哪些区域需平台审核。保洁员可设置服务区域，派单候选只列出服务该酒店所在区域的保洁员。

**公众号 / 小程序**

- 每个机构可对接自己的公众号或小程序，配置存 `wx_account`。
- 进入时如何识别机构：公众号 H5 的地址里带机构标识；小程序按 `appid` 反查机构。酒店二维码沿用「机构 + 酒店」的做法，但改成服务端生成的短码，不把参数加密后放在链接里。
- 公众号菜单：按机构开通的应用，把各应用的菜单片段合并成默认菜单，机构可调整后推送。
- 消息模板 id 每个公众号 / 小程序都不同，按账号保存；发送时按机构取对应账号。
- 小程序订阅消息是一次授权发一条，和公众号模板消息的规则不同，通知逻辑要分开处理。
- 机构自有小程序需要为每个 `appid` 单独发布同一套代码。V1 先支持机构自有公众号 + 一个平台小程序；机构自有小程序的发布方式待定，见 3.3。

**控制台**

- 组件登记在 `console_widget`，归属到应用，区分电脑端和手机端。
- 每个应用带一份默认布局。机构没有自定义时，控制台 = 所开通应用默认布局的合并。
- 机构可自行增减、排序，存到 `console_layout`。
- 接口返回前按「机构开通的应用 ∩ 当前用户权限」过滤。
- 手机端首页的功能入口来自 `app_mobile_entry`，同样按上述规则过滤，所以开通新应用后入口自动出现。

**保洁流程与状态**

```
酒店录单（机构可代录）
  → 待派单 → 已派单 → 已到场 → 待验收 → 已完成
                 ↑        │           │
                 └─ 撤回 ─┘           └─ 退回重做 → 已派单
  任意未完成状态可：取消、报异常
```

- 明细全部完成或取消后，主单自动完成。
- 下单时把 `clean_price` 的单价写入明细，之后调价不影响已有订单。
- 派单候选按保洁员评分降序，同时返回在手单量。评分取最近 N 条评价的平均值，没有评价时用默认分；N 和默认分做成参数。
- 派单、完工、验收这类操作要防重复提交，状态变更用带原状态条件的更新。
- 不做保洁员抢单，不做线上支付。金额只做记录，机构手动标记已收。

**平台统计**

按区域、机构、月份汇总单量和金额，可导出。数据量上来后改成定时汇总到统计表，不直接扫订单表。

### 2.7 数据迁移

| 数据 | 做法 |
| --- | --- |
| 字典、参数 | 只导入通用项和保洁相关项 |
| 机构 | 先迁使用保洁的机构；其他机构随各自业务线迁移 |
| 用户、角色 | 随机构迁移；旧密码哈希不沿用，首次登录用验证码 |
| 酒店、房间、酒店人员、保洁员 | 随机构迁移；酒店的区域需补填 |
| 历史保洁单 | 是否迁移、迁多久的范围待定；建议至少迁未结清的 |
| 公众号配置 | 随机构迁移，密钥重新录入并顺便更换 |

旧系统在迁移期间继续运行，一条业务线在新平台验收后再切换。

## 3. 后续需要考虑的事

### 3.1 新应用接入

- 每个应用是一个独立的 Maven 模块和一个小程序分包，自带菜单、手机端入口、公众号菜单片段、控制台组件、默认角色。
- 各项服务的骨架相同：酒店下单 → 机构派给人 → 执行 → 验收评价 → 对账。V1 在保洁模块里实现时，派单、评价、对账、消息的代码边界要划清楚，但不必现在就抽成通用模块；等第二个应用接入时再抽，避免凭一个样本过早抽象。
- 同一机构开通多个应用时共用同一批酒店。旧系统里洗涤用的是单独的客户表，迁移洗涤时要并入酒店表。
- 服务人员会有多种身份（保洁员、司机、维修工），同一个人可能兼任。V1 的 `cleaner` 是「用户 + 身份」的结构，后面的身份照此扩展；评分、在手单量按身份分别统计。

### 3.2 各应用的特殊点

| 应用 | 需要提前留意 |
| --- | --- |
| 酒店接送 | 司机实时定位、车辆证照到期提醒、预约时间限制；旧系统已有完整实现可参照 |
| 洗涤 | RFID 布草出入库、一客一价、Lodop 打印、欠款 |
| 维修 | 工单带故障描述和照片、上门时间预约、配件和费用明细，金额在完工后才确定，与保洁的「下单即定价」不同 |
| 配餐 | 商品 / 菜单、起送和配送、可能需要线上支付；旧系统的电商模块可参照 |

### 3.3 微信

- 机构自有小程序数量多了以后，需要接入微信开放平台的第三方平台，做授权和批量代发布。V1 只要保证「按 appid 识别机构」这一点，后面就能平滑接入。
- 配餐如果要线上支付，需要引入框架的支付模块，并考虑平台、机构之间的分账。V1 不要把「金额只是记录」写死在订单模型里。

### 3.4 数据与权限

- 同一家酒店可能被两个机构各自录入，系统不强制去重。可以在酒店上留一个可选的统一标识字段（如营业执照号），以后平台想做去重统计时有依据。
- 机构做大后可能需要「派单员只管某几个区域」，即按区域的数据权限。V1 不做，但区域字段要落在酒店和订单上，方便以后加条件。
- 字典按机构覆盖、参数按机构取值，旧系统有这个能力，V1 先不做，看是否有机构提出需求。

### 3.5 工程

- 订单表按 `tenant_id + hotel_id + date` 建索引；状态查询另建索引。
- 缓存放 Redis，保证可以多实例部署。
- 引入数据库变更脚本管理和核心流程的自动化测试。
- 密钥统一放配置中心或环境变量，不进仓库；微信密钥加密存储，接口不回显。
- 关键操作留审计日志：派单、改派、验收、收款标记、机构审核、应用开通。
- 单体先行。某个应用负载明显偏高时再单独拆出部署，框架有对应的微服务版本。

### 3.6 待定事项

1. 机构自有小程序的发布方式：逐个手动发布，还是直接接第三方平台。
2. 历史保洁单迁移的范围。
3. 评分的计算窗口和默认分。
4. 框架版本的最终选定，以及 2.4 中五处改动对照源码的验证结果。
