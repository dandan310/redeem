# 平台业务模型、功能点与改造计划

> **注意：本文档中「酒店提为平台级档案 / 服务关系」的设计已作废。** 最新结论是酒店由机构各自维护，见 [酒店服务平台架构与V1改造说明](./architecture-and-v1.md)。

> 用途：股东对齐会材料。
> 依据：线上后台只读调研 + 现有 Node 后端源码通读（约 1.7 万行、99 张数据表、约 325 个接口）。
> 配套文档：[基础数据结构](./base-data-structure.md)、[第一版开发细节](./v1-shared-cleaning-plan.md)。
> 工期为粗估，按 2 名后端 + 1 名前端/小程序开发的投入假设，需要按实际团队校准。

## 一、结论先行

1. **现有系统已经跑通了五条业务线**（客房保洁、酒店接送、洗涤厂、电商点餐、账单），但它是「一家运营方一套后台」的结构，做不了「众包商自己注册、自己管人、平台统一看」。
2. **新平台的定位**：我们做平台，景区内的服务商（先是保洁众包商，之后是车队、洗涤厂）作为租户入驻，按开通的应用使用功能；酒店是各项服务共同的客户。
3. **第一版只做共享保洁**，但底座按多应用设计，后续每搬一条业务线只是「加一个应用」，不用再动底座。
4. **技术路线**：用 Java 开源框架芋道 ruoyi-vue-pro 做底座，手机端用一套小程序/H5 代码。旧系统在迁移期间继续运行，业务线逐条切换。
5. **粗估工期**：第一版（底座 + 共享保洁）约 3.5～4 个月；之后接送、洗涤各约 1.5～2 个月。
6. **需要股东拍板的事项**见第七节，共 5 项。

## 二、现有系统现状

### 2.1 已有业务线

| 应用 | 已实现的功能 | 使用方 |
| --- | --- | --- |
| 客房保洁 | 酒店按天录保洁单、逐间房明细；派单（单间/整单）、保洁员自己接单、撤单、完工、查房、异常、取消；按房间定价；标记收款；公众号消息提醒；月度统计 | 保洁机构、酒店、保洁员 |
| 酒店接送 | 车队、司机、车辆（保险/年检到期提醒）；接机/送机/商户接客订单；预约、派单、接单、出发、到达、异常；司机定位；酒店月账单；导出 | 车队、酒店、司机 |
| 洗涤厂 | 客户（酒店）及一客一价；每日布草送洗/送回单；RFID 布草入库出库；核对；欠款；月账单导出与打印 | 洗涤厂、酒店 |
| 电商 / 在线点餐 / 酒吧 | 商家、商品分类与规格、购物车、微信支付与退款、订单打印、评价与审核、会员存酒与余额 | 商家、顾客 |
| 账单管理 | 收入/成本台账、标签分类、成本分析、账单共享、绩效工资 | 内部 |
| 河流监测 | 河流、断面、监测数据录入与图表 | 与酒店服务无关的独立项目 |
| 平台底座 | 机构、应用、菜单与权限、角色、用户、字典、系统参数、公众号/小程序配置、通知、定时任务、工作台 | 管理员 |

规模：用户约 3700，酒店约 110 家，洗涤客户约 130 家，机构 13 个。

### 2.2 现有业务模型

```
机构（一家运营方）──开通──> 应用（保洁 / 接送 / 洗涤 …）
   │
   ├── 用户（一个用户只属于一个机构）── 角色 ── 权限
   ├── 酒店（每个机构各建各的）── 房间、酒店人员
   ├── 保洁员 / 司机（都是「用户」加一个身份）
   └── 订单（保洁单、接送单、布草单 …）
```

酒店通过机构发的专属链接/二维码进入公众号页面下单，这个链接里绑定了「机构 + 酒店」。

### 2.3 现有模型为什么撑不住共享保洁

| 问题 | 表现 |
| --- | --- |
| 没有平台层 | 没有「景区」概念；机构只能由我们在后台手工开，不能自助注册 |
| 酒店信息冗余 | 酒店记录带「所属机构」，只在本机构内可见：同一机构内保洁和接送共用，但不同机构服务同一家酒店时要各建一条；洗涤另用「客户」表，与酒店表无关联。结果是同一家酒店有多份互不相通的档案，改信息要改多处，也无法看到一家酒店用了我们哪些服务。新模式下服务商都是独立租户，这会成为常态，所以酒店必须提为平台级 |
| 一个用户只能属于一个机构 | 同一个手机号不能在两家服务商下工作 |
| 手机端是写死的 | 每个角色的页面固定，新增应用要改代码、改公众号菜单 |
| 缺评价和排序 | 保洁没有评价，派单只能靠人记 |

### 2.4 技术现状与风险

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| 接口存在注入漏洞 | 查询条件和更新语句由字符串直接拼接，全系统通用 | 新系统用参数化查询根治；旧系统在迁移期内尽量不对外暴露新入口 |
| 密钥随代码存放 | 数据库口令、微信支付证书、登录私钥都在代码包里 | **建议现在就更换**，代码包已经在多处流转 |
| 密码保护弱 | 密码无盐哈希，默认密码是手机号后六位 | 新系统换强哈希，迁移后用验证码重置 |
| 无自动化测试、无数据库变更记录 | 改动靠人工回归 | 新系统建立测试和变更脚本 |
| 单进程、单库 | 一个异常可能影响全部业务线 | 新系统按模块隔离 |

这些是换技术栈的主要理由：继续在旧代码上叠加多租户，风险和成本都比重建底座高。

## 三、目标业务模型

### 3.1 一张图

```
平台（我们）
 ├── 景区：四姑娘山（管理员维护，后续可加）
 ├── 酒店/民宿（平台级档案，一家酒店全平台只有一份；可标注所属景区）
 │
 ├── 应用：共享保洁 │ 酒店接送 │ 洗涤 │ 账单 │ …（管理员维护）
 │
 └── 租户（服务商：众包商 / 车队 / 洗涤厂）—— 自助注册，平台审核
       ├── 选择景区、开通一个或多个应用
       ├── 自己的人员：管理员、派单员、保洁员、司机 …
       ├── 自己对接的酒店（服务关系）、自己的价格
       └── 自己的订单、评价、账目
```

### 3.2 核心规则

| 规则 | 内容 |
| --- | --- |
| 酒店是平台级档案 | 不属于任何服务商，全平台一店一份 |
| 景区是酒店的可选属性 | 每个应用有开关「是否按景区管理」：共享保洁开启，对接酒店时要求酒店已标注景区且在众包商获批的服务景区内；洗涤、接送关闭，景区可留空 |
| 众包商可服务多个景区 | 众包商与景区多对多，新增需平台审核；酒店、保洁员、派单员权限、报表都可按景区划分，派单时只列出服务该景区的保洁员 |
| 景区按「服务区域」建模 | 景区是服务区域的一种类型，以后可加城市、片区；其他业务到外地开展时打开应用开关即可 |
| 众包商自己对接酒店 | 众包商把酒店加为自己的服务对象：酒店已有档案则绑定，没有则新建 |
| 一家酒店的保洁只能对接一家众包商 | 「酒店 + 应用」只能有一个生效的服务关系；已被绑定的酒店，其他众包商无法再绑，换绑由平台处理 |
| 同一家酒店可以用多种服务 | 保洁对接 A 众包商、接送对接 B 车队、洗涤对接 C 洗涤厂，互不冲突 |
| 价格由服务商定 | 众包商给自己对接的酒店按房型定价；下单时价格写入订单留痕 |
| 派单 | 酒店按入住、离店情况录单；众包商派单员手动派给保洁员，候选人按评分从高到低排 |
| 评价 | 酒店验收时给保洁员打分，累计成保洁员评分和众包商评分 |
| 不经手资金 | 平台只记录单量和金额，不做线上支付；平台收入来自第三方返点 |
| 数据可见范围 | 租户只看自己的；酒店只看自己店的；平台管理员看全部 |

### 3.3 角色

| 角色 | 入口 | 主要动作 |
| --- | --- | --- |
| 平台管理员 | 电脑后台 + 手机 | 景区、应用、模板；审核租户；酒店换绑；全平台报表与返点统计 |
| 租户管理员（众包商负责人） | 手机为主 | 注册、选景区、开通应用、对接酒店、定价、管人、看账 |
| 派单员 | 手机 | 看待派单、派单、改派、处理异常 |
| 保洁员 | 手机 | 接收任务、到场打卡、完工拍照 |
| 酒店人员 | 手机 | 录单、验收、评价、看历史和月账 |

### 3.4 共享保洁业务流程

```
众包商注册 → 平台审核 → 开通「共享保洁」→ 录保洁员、对接酒店、定价
                                                   │
酒店录单（勾选房间：退房打扫 / 续住打扫）────────────┘
   → 进入所对接众包商的待派单列表
   → 派单员派给保洁员（按评分排序，显示在手单量）
   → 保洁员到场打卡 → 完工拍照
   → 酒店验收 + 评价（可退回重做 / 报异常）
   → 订单计入月度对账与平台统计
```

### 3.5 新旧对照

| 现有 | 新平台 | 变化 |
| --- | --- | --- |
| 机构 | 租户 | 由后台开通改为自助注册 + 审核 |
| 应用、机构-应用 | 应用、租户-应用 | 保留；手机端入口跟着应用自动出现 |
| 酒店（各机构各一份） | 酒店（平台级）+ 服务关系 | 一店一档，多种服务共用 |
| 保洁员、司机 | 用户 + 身份 | 增加评分、服务景区 |
| 保洁订单、明细 | 基本沿用 | 增加到场打卡、验收、评价、价格快照 |
| 无 | 景区 | 新增 |
| 无 | 评价 | 新增（电商已有评价，可借鉴） |
| 微信支付（电商用） | 第一版不带 | 电商迁移时再评估 |

### 4.4 后续应用

| 顺序 | 应用 | 主要功能点 | 能复用第一版的部分 |
| --- | --- | --- | --- |
| 2 | 酒店接送 / 车队 | 车队、司机、车辆与证照到期提醒；接送机订单的预约、派单、出发、到达、异常；司机定位；酒店月账单 | 酒店档案、服务关系、派单与状态流转、评价、对账、消息、工作台 |
| 3 | 洗涤厂 | 客户一客一价；每日送洗/送回单；RFID 布草出入库；核对；欠款；月账单打印 | 酒店档案、服务关系、定价、对账、导出 |
| 4 | 账单与绩效 | 收入/成本台账、标签、成本分析、绩效工资 | 做成各应用通用的财务模块 |
| 5 | 电商 / 点餐 / 酒吧 | 商家、商品、购物车、支付退款、评价、会员存酒 | 评价、消息；支付要重新接入 |
| — | 河流监测 | 建议留在旧系统，不迁移 | 与平台定位无关 |

三条酒店服务线（保洁、接送、洗涤）的共同骨架是：**服务商 → 对接酒店 → 定价 → 酒店下单 → 派给人 → 完成 → 评价 → 月度对账**。第一版把这条骨架做成通用能力，后两条线主要是换单据内容，所以工期比第一版短。

顺序这样排的理由：接送和保洁的流程最像，复用最多；洗涤涉及 RFID 硬件和打印，放第三；电商带支付，和「不经手资金」的方向不同，最后评估是否迁移。

## 五、改造计划

### 5.1 阶段与粗估工期

| 阶段 | 内容 | 粗估 | 交付物 |
| --- | --- | --- | --- |
| 0 | 底座搭建：部署框架、裁剪模块、接上传和短信、手机端工程 | 1 周 | 可登录的空后台和空小程序 |
| 1 | 多租户与基础数据：应用、租户多应用、注册审核、景区、管理员跨租户、字典和参数移植 | 3 周 | 众包商可注册并被审核开通 |
| 2 | 手机端骨架：登录、多租户选择、动态工作台、应用模板、消息通道 | 3 周 | 不同角色登录看到各自入口 |
| 3 | 保洁主数据：酒店档案与服务关系、房型、保洁员、定价 | 2 周 | 众包商可录人、对接酒店、定价 |
| 4 | 保洁订单与评价：录单、派单、执行、验收、评价、消息 | 4 周 | 全流程可走通 |
| 5 | 对账与统计：月账单、平台报表、导出 | 2 周 | 返点数据可导出 |
| 6 | 试点上线：四姑娘山 1～2 家众包商试运行、修问题、小程序审核 | 2 周 | 正式可用 |
| 合计 | 第一版 | 约 3.5～4 个月 | |
| 7 | 酒店接送 / 车队应用 | 1.5～2 个月 | |
| 8 | 洗涤厂应用 | 1.5～2 个月 | |
| 9 | 账单与绩效；电商评估 | 另行排期 | |

小程序备案和审核、短信签名审核需要提前办理，建议阶段 0 就启动，否则会卡在阶段 6。

### 5.2 新旧系统并行

- 旧系统在整个迁移期继续承载现有业务，不做大改，只修安全问题。
- 按应用逐条切换：一条业务线在新平台验收通过后，把这条线的机构、人员、酒店和必要的历史数据导入，旧系统上对应功能改为只读。
- 现有保洁机构作为新平台的第一批租户，和四姑娘山的新众包商一起验证。
- 酒店数据迁移时要做合并：同一家酒店在旧系统多个机构下的多份档案，合成一份平台档案。

### 5.3 为什么选开源框架

| 项 | 说明 |
| --- | --- |
| 现成可用 | 租户隔离、权限、字典、参数、定时任务、上传、短信、站内信、公众号管理、代码生成，约占底座工作量的七成 |
| 需要改造 | 一个租户开通多个应用；租户自助注册 |
| 需要新写 | 景区与酒店服务关系、手机端动态工作台、全部保洁业务 |
| 许可 | MIT，可商用 |
| 延展 | 先单体部署；业务量明显上来后可切到同一作者的微服务版本 |

框架细节基于我对该框架的了解，尚未逐项对照源码验证，阶段 0 第一件事是做这项验证。

## 六、主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 酒店不愿用手机录单 | 没有订单数据，返点无从统计 | 录单做到「勾房间即可」；保留众包商代录入口 |
| 评分影响保洁员收入引发争议 | 众包商抵触 | 评分只用于排序建议，派单权仍在派单员；评分规则公开 |
| 一店一家规则下的抢绑 | 众包商抢先绑定并不实际服务 | 绑定需酒店扫码确认；长期无单自动提醒平台处理 |
| 小程序资质与审核周期 | 上线延期 | 提前办理 |
| 旧系统安全问题在迁移期被利用 | 数据泄露 | 立即更换密钥；限制后台访问来源 |
| 工期估计偏乐观 | 延期 | 第一版严格限定范围，见 4.3 |

## 七、需要股东确认的事项

1. **投入**：是否按「2 后端 + 1 前端/小程序」配置推进，第一版 3.5～4 个月的预期是否接受。
2. **对租户是否收费**：众包商入驻和使用是否免费；这决定要不要做套餐和计费。目前按「免费，平台只拿第三方返点」规划。
3. **返点口径**：第三方是谁、按单量还是金额、结算周期。这决定平台报表要出哪些数字。
4. **小程序主体**：用哪家公司的主体申请平台小程序和公众号。
5. **迁移范围**：是否同意河流监测留在旧系统、电商最后再评估。
