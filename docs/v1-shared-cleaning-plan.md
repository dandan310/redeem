# 第一版规划：多租户底座 + 共享保洁

> 前置文档：[现有系统基础数据结构梳理](./base-data-structure.md)
> 框架适配部分基于我对芋道 ruoyi-vue-pro 的了解，这次没有拉代码逐项核对，类名和功能点在选定版本后需要对着源码确认一遍。

## 1. 业务模型

### 1.1 角色

| 角色 | 是谁 | 主要入口 | 做什么 |
| --- | --- | --- | --- |
| 平台管理员 | 我们 | PC 后台 + 手机 | 维护景区、应用、小程序/公众号模板；审核众包商；看全平台数据 |
| 租户管理员 | 众包商负责人 | 手机为主，PC 可选 | 注册、选景区、开通应用、录入保洁员、派单、看账 |
| 保洁员 | 众包商下的人员 | 手机 | 接单、到场、完工拍照 |
| 下单方 | 景区内的酒店/民宿 | 手机 | 发保洁需求、验收 |

### 1.2 数据归属（多租户的核心）

多租户框架默认「每条数据属于一个租户，租户之间互相看不到」。共享保洁有三类数据，不能都按这个规则走：

| 类别 | 数据 | 归属 | 隔离方式 |
| --- | --- | --- | --- |
| 平台公共 | 景区、应用、应用的菜单与手机端模板、字典、系统参数 | 平台 | 不带租户，所有租户只读 |
| 租户私有 | 保洁员、租户的角色与人员、租户的公众号配置 | 众包商 | 按租户自动隔离 |
| 跨租户共享 | 酒店/民宿、房型、保洁订单 | 景区 | 不走自动隔离，按「景区 + 状态 + 接单租户」手写过滤 |

第三类是「共享」的由来：酒店发出的订单先进景区的订单池，该景区下所有众包商都能看到；被某个众包商接走后，订单写上接单租户，其他众包商就看不到了。

```
景区 scenic ──< 租户-景区 >── 租户 tenant（众包商）──< 租户-应用 >── 应用 app
   │                              │
   ├──< 酒店 hotel ──< 房间/房型    └──< 保洁员 cleaner（→ 用户）
   │        │
   └──< 保洁订单 order：scenic_id, hotel_id, 状态, 接单 tenant_id, cleaner_id
```

### 1.3 需要你先定的四件事

这四件事会改变表结构或开发量，我先按「建议」一栏做的规划：

| 问题 | 建议 | 影响 |
| --- | --- | --- |
| 酒店归谁？ | 归景区（平台公共），酒店自己注册或管理员录入 | 如果酒店归某个众包商私有，就没有订单池，变成普通的租户内派单 |
| 抢单还是派单？ | 第一版：众包商管理员从订单池接单，再派给自己的保洁员；保洁员直接抢单留到后面 | 决定并发控制和通知的做法 |
| 第一版要不要线上支付？ | 不做，只记应收/已收，线下结算 | 线上支付涉及分账（平台、众包商、保洁员），工作量大 |
| 小程序是一个还是每个租户一个？ | 第一版只做一个平台小程序，所有租户共用 | 见 3.2 |

## 2. 多租户改造点

芋道的多租户是「租户 + 租户套餐」，和我们的需求有三处不一致：

**一、一个租户要能开通多个应用。** 芋道里一个租户只能绑一个套餐（一组菜单）。需要改成：

- 新增「应用」表：编码、名称、PC 菜单集合、手机端模板（见 3.1）。
- 新增「租户-应用」关联表，租户的可用菜单 = 所开通应用的菜单并集。
- 改动集中在租户服务里按套餐取菜单、套餐变更后同步租户角色菜单这两处，范围不大。
- 现有系统的「应用管理」「机构-应用」正好平移过来。

**二、租户自助注册。** 芋道的租户由管理员在后台创建。需要新增：手机端注册申请（公司名、联系人、手机号、营业执照、选择景区）→ 平台审核 → 通过后复用现成的「创建租户」逻辑，自动建租户、租户管理员账号和默认角色，并开通「共享保洁」应用。

**三、平台管理员跨租户。** 一个管理员账号要能看所有租户的数据。芋道的系统租户 + 超级管理员可以承担这个角色，新版本支持管理员切换到指定租户查看；全平台汇总报表需要单独写不带租户过滤的查询。

**登录时怎么确定租户：** 手机号登录后查这个手机号属于哪些租户，只有一个就直接进，多个就让用户选（同一个人给两家众包商干活是可能的）。

## 3. 手机端与小程序/公众号

### 3.1 「按应用自动生成模板」怎么实现

做法是**一套手机端代码包含所有应用的页面，显示什么由服务端配置决定**，而不是给每个租户生成一套代码：

- 每个应用带一份**手机端模板**：首页布局、底部导航、功能入口列表（图标、名称、页面路径、所需权限）、各角色看到的入口。
- 手机端登录后请求「我的工作台」接口，服务端按「租户开通的应用 ∩ 用户角色权限」返回入口列表，前端渲染。
- 租户开通新应用后，下次打开自动多出该应用的入口，无需发版。
- 租户可以覆盖少量内容：名称、Logo、主题色。
- 现有系统的「工作台组件 / 工作台组装」就是这个思路的 PC 版，可以沿用其表结构做成手机版。

之后上车队管理、洗涤厂管理，就是：往代码里加这个应用的页面 → 发一次版 → 后台新增应用和模板 → 租户勾选即可。

### 3.2 小程序

微信小程序每个都要单独审核发布，不能在运行时凭空生成。两条路：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 共用一个平台小程序（第一版） | 我们自己的小程序，所有租户、所有角色共用，登录后按租户和角色显示内容 | 上线快，订阅消息模板只配一次 |
| 租户独立品牌小程序（后期） | 注册微信开放平台「第三方平台」，租户扫码授权，我们用同一套模板代码批量代发布，租户 id 写在扩展配置里 | 租户要自己的名字和 Logo 时再做，需要资质和审核 |

### 3.3 公众号

公众号可以按应用自动生成：

- 每个应用带一份公众号菜单模板和消息模板清单。
- 租户在后台填自己的公众号配置，开通应用后系统把各应用的菜单模板合并，调微信接口推上去。现有系统的 `menu_obj` 和「生成菜单」就是这个功能。
- 第一版只接平台自己的公众号用于消息提醒即可，租户自有公众号放后面。

### 3.4 移动端技术

用 uni-app（Vue 3）写一套，发小程序和 H5（公众号内打开）。租户管理员的操作（录保洁员、派单、看账）都要有手机页面；PC 后台第一版只保证平台管理员用。

## 4. 第一版功能点与开发顺序

按依赖关系排，前一阶段是后一阶段的前提。

### 阶段 0：底座搭建

- 部署 ruoyi-vue-pro，只保留系统、基础设施、公众号模块，裁掉商城、CRM、ERP、工作流等。
- 接七牛云上传、短信验证码。
- 搭 uni-app 工程骨架。

### 阶段 1：多租户与基础数据移植

1. 应用表、租户-应用关联，菜单按应用取并集（2 节第一点）。
2. 平台管理员跨租户查看。
3. 基础数据移植：
   - 字典、系统参数：筛掉其他业务线专用的，导入通用的和保洁用的。
   - 应用：9 个应用先建档，只有「共享保洁」启用，其余等对应业务搬过来再启用。
   - 机构 → 租户：结构平移。现有 13 个机构的数据建议跟着各自的业务线一起搬，不在第一版一次性导入，否则这些租户登录进来没有可用功能。
   - 菜单和权限码：**不能直接搬**，它们对应的是旧前端页面。新系统的菜单随每个应用的页面一起新建。
   - 用户：密码算法不同，随所属机构一起迁移，迁移后用手机验证码登录。
4. 租户注册申请、平台审核、自动开通。

### 阶段 2：手机端骨架

1. 小程序手机号一键登录、短信验证码登录、多租户选择。
2. 应用的手机端模板配置（后台）和「我的工作台」接口。
3. 手机端首页按配置渲染、个人中心、消息列表。
4. 平台小程序与公众号的配置、订阅消息/模板消息发送通道。

### 阶段 3：保洁主数据

1. 景区管理（平台）：先录四姑娘山。
2. 租户-景区：注册时选择，之后可申请增加，平台审核。
3. 酒店/民宿、房型或房间、酒店人员（负责人/普通）。
4. 保洁员（租户）：姓名、手机号、证件、服务景区、状态；录入时自动建用户并绑定「保洁员」角色。
5. 保洁价格：按景区 + 房型定价（谁定价需确认，建议第一版平台统一定）。

### 阶段 4：保洁订单

1. 酒店发单：房间、保洁类型、期望时间、备注、照片。
2. 景区订单池：众包商接单（并发控制，一单只能被一家接）。
3. 众包商派单给保洁员，可改派。
4. 保洁员：到场打卡 → 完工拍照提交。
5. 酒店验收；异常上报与取消。
6. 各环节的消息提醒。

状态沿用现有字典：待接单 → 已接单 → 已完成，另有异常、已取消；收款状态为待收款 / 已收款。

### 阶段 5：结算与统计

1. 订单应收、标记已收；按酒店、按众包商的月度对账单。
2. 工作台统计：平台看全景区，众包商看自己，保洁员看个人单量。

### 第一版不做

线上支付与分账、保洁员直接抢单、租户独立品牌小程序、租户自有公众号、评价体系、其他业务应用。

## 5. 开源框架适配情况

| 需求 | ruoyi-vue-pro 现状 | 工作量 |
| --- | --- | --- |
| 租户、行级隔离 | 有，自动加租户条件，可对指定表或方法关闭 | 直接用 |
| 租户开通多个应用 | 只有单套餐 | **改造**，新增 2 张表 + 改租户菜单逻辑 |
| 租户自助注册 + 审核 | 只有后台创建 | **新增**，复用创建租户逻辑 |
| 平台管理员跨租户 | 有系统租户和超级管理员，新版可切换租户 | 小改，汇总报表另写 |
| 跨租户的订单池 | 无此概念 | **新增**，相关表不走自动隔离，手写过滤 |
| 菜单、角色、按钮权限 | 有 | 直接用 |
| 字典、参数配置、定时任务、操作日志 | 有 | 直接用 |
| 文件上传（七牛）、短信 | 有 | 配置即可 |
| 站内信、WebSocket | 有 | 直接用 |
| 公众号多账号、菜单、模板消息 | 有（公众号模块） | 小改：按应用模板自动合并菜单 |
| 小程序登录、订阅消息 | 会员端有，后台用户端不全 | 小改：给后台用户补小程序手机号登录 |
| 手机端按应用动态生成入口 | 无（商城有店铺装修，思路可借鉴） | **新增**：模板配置 + 工作台接口 + 前端渲染 |
| 手机端工程 | 有商城版和管理后台版 uni-app | 只能参考登录、请求封装，业务页面全部新写 |
| 景区、酒店、保洁员、价格 | 无 | 新增，用代码生成器出增删改查 |
| 保洁订单流程 | 无 | 新增，第一版的主要业务开发量 |
| 支付、分账 | 有支付模块，无分账 | 第一版不做 |

**人员放哪张表：** 上一份文档里我提过保洁员可以放会员表，现在建议改为：众包商管理员、保洁员、酒店人员都放后台用户表。他们都需要「属于某个租户 + 有角色权限 + 被派单」，这些是后台用户体系才有的；会员表留给以后可能出现的游客端。

**结论：** 底座约七成能力现成可用，需要动框架本身的只有「多应用」和「租户注册」两处，改动集中；主要工作量在手机端和保洁订单，这部分用哪个框架都得自己写。
