1业务模型

现有系统以「机构」为中心：每个机构是一家运营方，各自建酒店、各自管人。重构后在机构之上加一层平台，把酒店提为平台级档案。

现有模型

机构（运营方，后台手工开通，现有 13 个）
应用机构开通哪些应用，就有哪些菜单
用户 / 角色一个用户只属于一个机构
酒店每个机构各建一份
保洁员 / 司机用户 + 身份
订单保洁单、接送单、布草单……

酒店记录带「所属机构」，只在本机构内可见。多家机构服务同一家酒店时，每家都要各建一条；洗涤还另用一张「客户」表。详见基础数据一节。

重构后模型

平台（我们）
景区管理员维护，先有四姑娘山；酒店的可选属性
应用保洁 / 接送 / 洗涤……
酒店档案平台级，全平台一店一份；可标注所属景区
服务关系：酒店 + 应用 → 只能对接一家租户
租户（众包商，自助注册 + 平台审核）
开通的应用可多个
人员管理员、派单员、保洁员
对接的酒店 + 定价
订单 / 评价 / 对账

同一家酒店可以保洁对接 A 众包商、接送对接 B 车队，互不冲突。

已确定的业务规则

规则内容
酒店是平台级档案不属于任何众包商，全平台一店一份。
景区是酒店的可选属性共享保洁要求酒店必须标注景区；洗涤、接送目前不要求，可以留空。
众包商可服务多个景区众包商申请服务景区，平台审核；名下的酒店、保洁员、派单和报表都可按景区划分。
众包商自己对接酒店酒店已有档案则绑定，没有则新建。
一店一家一家酒店的保洁只能对接一家众包商；换绑由平台处理。
手动派单酒店录单，众包商派单员指派保洁员，候选人按评分从高到低排。
众包商定价按酒店、房型定价；下单时价格写入订单留痕。
不经手资金只记录单量和金额，不做线上支付；平台收入来自第三方返点。

2系统设置

现有后台的「系统设置」是整套系统的底座。其中应用管理、自定义工作台、公众号/小程序三项是平台化的关键，重构时保留并升级。

应用管理

一个应用 = 一组菜单和操作权限。机构开通应用后，才能给自己的角色分配这些菜单。

  • 现有 9 个应用：客房保洁、酒店接送、洗涤厂、酒店线上订单、电商、酒吧、账单、河流监测、开发管理平台
  • 机构可开通多个应用
  • 目前只管电脑后台的菜单，手机端页面不在应用里

自定义工作台

首页看板可以拼装：先有一批统计组件，再把组件按宽度、高度、顺序组装成一个工作台，分配给机构。

  • 现有 23 个组件：客房统计、接送统计、布草营收、热销商品、待办事项、快捷方式等
  • 现有 5 套工作台：客房、洗涤厂、电商、河流检测、开发平台
  • 一个机构只能用一套工作台；组件是否显示还受权限控制
  • 只有电脑版

公众号 / 小程序

按机构登记微信公众号或小程序的配置，手机端从公众号网页进入。

  • 配置项：类型、账号参数、手机端网址、消息模板、公众号菜单、微信支付商户信息
  • 公众号菜单在后台编辑后一键推送到微信
  • 新订单、完工等通过公众号模板消息提醒
  • 酒店用专属链接/二维码进入，链接里绑定了机构和酒店
  • 现有 3 个账号；菜单和页面是按机构手工配的

现有问题：酒店信息冗余

同机构内共用

一个机构同时开通保洁和接送时，两个应用用的是同一批酒店，不重复。

跨机构各建一份

酒店记录带「所属机构」，别的机构看不到。保洁和接送由不同机构承接时，同一家酒店要各建一条。

洗涤另有一张表

洗涤用的是「客户管理」，和酒店表没有关联，同一家酒店又是一条独立记录。

后果：酒店改电话或换负责人要改多处；无法回答一家酒店用了哪几项服务、总共多少单；酒店人员的账号只能挂在一个机构下。新模式下众包商、车队、洗涤厂是各自独立的租户，这种重复会成为常态，所以酒店必须提为平台级档案：全平台一店一份，各服务商通过「服务关系」对接它。

景区怎么处理

景区描述的是酒店在哪里，不是保洁业务独有的东西。所以把它放在酒店档案上作为可选属性，是否必填由应用决定。

问题处理方式
只有保洁需要景区酒店档案的「所属景区」可以为空。每个应用有一个开关「是否按景区管理」：共享保洁开启，洗涤、接送关闭。
保洁如何保证有景区众包商对接酒店时校验两点：酒店已标注景区；该景区在众包商获批的服务景区内。不满足不能建立保洁服务关系。
旧酒店数据迁移时景区留空。只有要开通共享保洁的酒店才需要补填。
一个众包商做多个景区众包商与景区是多对多，新增景区需申请并由平台审核。名下酒店按景区分组；保洁员可设置服务哪些景区；派单时只列出服务该酒店所在景区的保洁员；派单员可限定只管某几个景区；报表可按景区拆分。
以后其他业务到外地开展景区在系统里作为「服务区域」的一种类型来建，以后可以增加城市、片区等类型。洗涤或接送需要按区域管理时，打开该应用的开关即可，不用改表结构。

接送里的「车队对接酒店」、洗涤里的「客户」，实际上都是酒店。重构后它们统一指向平台的酒店档案。

4共享保洁流程

主线不变：酒店用自己的账号下单，单据进入所对接的众包商，由派单员指派保洁员。底色标出的是重构后新增的环节。

1
众包商
注册入驻 新增

手机上提交资料、选择景区；平台审核通过后自动开通账号和「共享保洁」应用。

2
众包商
准备 沿用

录入保洁员、对接酒店、设置房型价格。酒店已被别家绑定时无法再绑。

3
酒店
录单 沿用

按当天离店、续住情况勾选房间，每间房一条明细。众包商也可以代录。

4
派单员
派单 沿用

收到新单提醒，逐间或整单指派，可改派、撤回。候选保洁员按评分排序并显示在手单量（新增）。

5
保洁员
到场打卡 新增

到达酒店后打卡，酒店和派单员可见。

6
保洁员
完工 沿用

拍照提交，酒店收到完工提醒。

7
酒店
验收与评价 新增

通过或退回重做；给保洁员打星、选标签、写评语。评价累计成保洁员和众包商的评分。

8
众包商
对账 沿用

按酒店出月账单，标记已收款。不走线上支付。

9
平台
统计 新增

按景区、众包商、月份汇总单量和金额，导出作为第三方返点依据。

与旧流程的差别

6整体架构

第一版只上线客房保洁。保洁、接送、洗涤的共同骨架是「服务商 → 对接酒店 → 定价 → 酒店下单 → 派给人 → 完成 → 评价 → 对账」，所以把这条骨架做成通用能力层，后面的应用主要是换单据内容。

第一版为后续应用提前做的事

预留点第一版怎么做以后接入新应用时
应用是功能包保洁的菜单、手机端模板、默认角色、消息模板都登记在「共享保洁」这个应用下新增一个应用及其模板，租户勾选即可用
景区按应用开关景区是酒店的可选属性；共享保洁开启「按景区管理」洗涤、接送默认不用；到外地开展时打开开关，或增加新的区域类型
服务关系带应用标识一店一家的规则按「酒店 + 应用」判断车队、洗涤厂对接酒店直接用同一张表
人员身份通用保洁员 = 用户 + 「保洁员」身份及评分司机是另一种身份，共用账号、评分、在手单量
流程骨架通用派单、状态流转、评价、对账做成各应用可调用的公共能力接送单、布草单只写自己的单据内容
手机端分包小程序里保洁页面单独成包，首页入口由服务端下发新应用加一个包、发一次版，入口自动出现
数据归属规则统一租户看自己的，酒店看自己店的，管理员看全部新应用的单据沿用同一套规则
代码按应用分模块底座、通用能力、保洁三者互不混写新应用是新模块；业务量大时可单独拆出部署

8需要确认的事项

  1. 投入：是否按 2 名后端 + 1 名前端/小程序开发推进，第一版 3.5～4 个月是否接受。
  2. 对租户是否收费：目前按「入驻和使用免费，平台只拿第三方返点」规划；如果要收费，需要加套餐和计费。
  3. 返点口径：第三方是谁、按单量还是金额、结算周期，决定平台报表出哪些数字。
  4. 小程序主体：用哪家公司的主体申请平台小程序和公众号。
  5. 迁移范围：是否同意河流监测留在旧系统、电商最后再评估。
